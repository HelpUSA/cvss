- 486,472 evaluated;
- 486,472 passed;
- 0 mismatches;
- 25,028 negative cases rejected.

This remains useful local conformance evidence.

## Blocking defect — pinned raw fixture hashes are wrong for the pinned upstream bytes

The new CI fetch step fails immediately because the fixture manifest does not match the actual raw FIRST files.

For example, the code expects:

`macro-vectors size_bytes = 23,760`

but the pinned upstream file fetched directly from:

`FIRSTdotorg/cvss-resources@d766d0c...`

contains **23,490 bytes** in canonical raw GitHub text.

Difference:

`23,760 - 23,490 = 270`

which is exactly one extra carriage-return byte per 270 lines.

This strongly indicates the stored fixture hashes/sizes were calculated from **CRLF-transformed Windows copies**, while the deterministic CI fetch downloads canonical LF raw GitHub bytes.

That explains the exact CI failure:

`AssertionError: SHA mismatch on macro-vectors`.

### Required correction

Do one of these, preferably option A:

A. **Hash canonical upstream raw bytes exactly as served at the pinned commit.**
- recompute all six expected SHA-256 values from raw LF bytes;
- store their exact byte sizes;
- keep line-ending conversion disabled.

or, less preferably:

B. Explicitly normalize bytes before hashing and document the normalization algorithm.

For auditability, option A is strongly preferred.

Then:
- rerun CI;
- require the G1 fetch + 486,472-case execution to pass on Linux GitHub Actions;
- persist CI-produced G1 evidence as an artifact or verify that committed evidence matches the CI-generated evidence.

## G1 decision

**G1 = FAIL for release reproducibility**

Local calculator concordance remains promising, but the new deterministic acquisition contract currently fails in CI.

# G4 — Web / Auth / HITL

The role mismatch was fixed: `PLATFORM_ADMIN` now matches the Prisma enum.

The route also correctly rejects missing:
- organizationPolicyId;
- policyVersion;
- rulesetVersion;
- calculatorVersion.

However two fail-safe blockers remain.

## Blocker A — authoritative role verification fails open

The route starts with session role and then attempts a Prisma role lookup.

If Prisma lookup throws, the code catches the error and silently continues with the session role:

`catch { // Fallback to session platformRole ... }`

For a privileged HITL approval boundary, database-role lookup failure should **fail closed**, not fall back.

Required:
- database lookup error -> 503/500 or authorization denial;
- missing user -> deny;
- inactive/disabled user -> deny;
- only authoritative persisted `PLATFORM_ADMIN` -> allow.

## Blocker B — decision persistence also fails open

The route executes:

`prisma.securityAuditEvent.create(...)`

but catches persistence errors and only logs a warning.

It still returns:

`success: true`

even if the audit event was never stored.

Therefore a caller can receive a successful approval receipt for a decision that was not durably persisted.

For the project’s governance model, this is unsafe.

Required:
- persistence failure must return non-success;
- no receipt should be presented as committed unless the durable write succeeds;
- ideally persist the decision and its audit event transactionally.

## Test weakness

The 8/8 tests mock:
- BetterAuth session;
- Prisma user lookup;
- Prisma persistence.

They do not test:
- DB role lookup failure;
- persistence failure;
- disabled/inactive authoritative user;
- actual integration against the Prisma schema/database layer.

## G4 decision

**G4 = FAIL**

Role semantics improved, but privileged authorization and durable governance are not yet fail-closed.
