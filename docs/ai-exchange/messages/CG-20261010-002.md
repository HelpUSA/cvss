### G4 — FAIL

The scientific route and local JCS helper improved, but the authentication/HITL claim is still not defensible.

#### Critical issue A: hard-coded auth-secret fallback

Current `web/src/lib/auth.ts` no longer fails closed when BETTER_AUTH_SECRET is missing/short.

It falls back to a known source-code string.

This regresses the earlier secure behavior.

Required:
- if BETTER_AUTH_SECRET is missing or <32 chars, throw and fail startup;
- no source-code secret fallback.

#### Critical issue B: Google login bypasses BetterAuth server session

Current `web/src/app/login/LoginForm.tsx` uses Google Identity Services in the browser, obtains an access token, fetches Google userinfo client-side, then stores the profile in localStorage and creates a client-controlled `helpus_auth_session` cookie.

That is not an authoritative BetterAuth server session.

Meanwhile `getActiveSession()` expects a real BetterAuth session via `auth.api.getSession()`.

These two flows are architecturally disconnected.

Required:
- use BetterAuth social sign-in/server callback flow;
- validate session server-side;
- verify account status and role server-side;
- no security decision based on localStorage or a client-created cookie.

#### Critical issue C: SuperAdmin authorization is not enforced

The analyze route itself correctly states:

`authorization_enforced_by_this_route: false`

No reproducible protected approve/reject mutation path was demonstrated.

PR #8 static Web code also contains client-side approval/rejection functions that write an in-memory history and display "Aprovado pelo Master" without authoritative server authorization.

Required:
- protected server-side approve/reject endpoint;
- unauthenticated -> reject;
- authenticated non-authorized -> reject;
- authorized role -> accept;
- reviewer identity loaded from authoritative server session;
- rationale/timestamp/assessment/policy/ruleset/calculator versions persisted;
- tests for all transitions.

Until then public/product wording must be:
`human review required`
not
`SuperAdmin enforcement proven`.

#### Critical issue D: static public code hard-codes the authorized account identity

PR #8 `index.html` contains a specific authorized master email and performs the authorization comparison in public client-side JavaScript.

Do not use public static JavaScript as the authorization boundary.

Move authorization entirely server-side and do not expose an authorized-account identifier merely to enforce access.
