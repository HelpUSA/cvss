# 2. CRITICAL / MUST-FIX

## C1. Blind-review violation: reference vector and score information are present in the expert portal

Current `experts/index.html` embeds scenario objects containing:
- `official_vector`
- `base_score`
- `base_severity`

and the portal code explicitly renders:

`cardOfficialVector.innerText = scn.official_vector`

This is incompatible with the declared blinded-review design.

Even if the displayed vector is called "official" rather than an AI prediction, exposing a reference vector or score can directly anchor expert judgments and contaminate the human ground truth.

### Required fix

The production expert bundle must contain **zero reference-answer data**:
- no official vector;
- no NVD/CNA score;
- no HelpUS score;
- no base severity;
- no adjudicated label;
- no answer-key metadata.

Reference answers must live in a logically and physically separate dataset/service that the expert-facing client cannot query.

Add an automated test that scans the production EDC bundle and fails if prohibited keys/tokens are present.

---

## C2. Anchoring bias: CR/IR/AR default to Medium instead of neutral/unanswered

The current portal initializes CR, IR and AR to `M` when no response exists:

`sel.value = r[m] || (["CR","IR","AR"].includes(m) ? "M" : "X")`

This silently preselects a substantive expert judgment.

### Required fix

All human-scored metrics must default to a true unanswered state, e.g. empty/null.

The user must actively choose each required metric.

Do not use `X` as a generic unanswered substitute when the metric semantics distinguish "Not Defined" from "not yet answered".

Add validation preventing final submit until all required fields are explicitly answered.

---

## C3. Current SHA-256 seal does not reliably cover the nested expert responses

The portal computes:

`JSON.stringify(payload, Object.keys(payload).sort())`

Using an array replacer causes JSON serialization to whitelist only the named keys at every object depth. Nested scenario IDs and metric keys not present in the top-level replacer can be omitted from the serialized material.

Therefore the displayed custody hash may **not commit to the actual nested response content**.

This invalidates the current claim of immutable cryptographic sealing.

### Required fix

Use a real recursive canonical JSON serializer (e.g. JCS / RFC 8785-compatible canonicalization already used elsewhere in the project) and hash the canonical bytes of the full response object.

Add a test that changes one nested metric/rationale and proves the hash changes.

Add a test that two semantically identical payloads with different object insertion order produce the same canonical hash.

---

## C4. localStorage is not an immutable EDC or custody system

The current portal:
- stores consent in `localStorage`;
- stores drafts in `localStorage`;
- stores the sealed submission in `localStorage`;
- lets the client compute its own hash;
- presents the result as "registered in custody log".

Any user can modify localStorage or execute JavaScript in the browser console.

There is currently no authoritative server-side receipt, authenticated submission endpoint, append-only audit store, independent timestamp, or server-held signing/HMAC key.

### Required fix

For real human collection:
- authenticated single-use participant token;
- TLS;
- server-side validation;
- authoritative server timestamp;
- recursive canonicalization;
- server-side HMAC/signature with segregated secret;
- append-only event trail;
- immutable submission state;
- external/checkpointed audit receipt;
- client receives a receipt derived from the server-accepted record.

Until that exists, the portal must be prominently labeled:

`SYNTHETIC DRY-RUN ONLY — NOT APPROVED FOR HUMAN RESEARCH DATA COLLECTION`

and all copy claiming "immutable custody", "sealed ground truth", or equivalent must be removed or qualified.

---

## C5. Portal permits sealing incomplete evaluations

The current `sealAndSubmitAll()` warns about missing scenarios but allows the user to continue after confirmation.

This conflicts with the pre-specified complete evaluation design and can alter denominators.

### Required fix

For the confirmatory workflow, incomplete submission must fail closed unless the frozen SAP explicitly defines partial-response handling.

If withdrawal is allowed, withdrawal must be a distinct event, not an incomplete "final submit".

---

## C6. Consent timestamp is not actually recorded at consent time

`confirmConsentAndProceed()` stores only:

`helpus_edc_consent_<expert> = true`

but does not store `helpus_edc_consent_time_<expert>`.

At final submission, the code falls back to `new Date().toISOString()`, creating a timestamp that can falsely appear to represent consent time.

### Required fix

Record consent event at the moment of consent on the authoritative server, with:
- consent document version/hash;
- participant pseudonymous ID;
- server timestamp;
- authentication context;
- signature/e-consent evidence;
- withdrawal/reconsent history.

Never fabricate a consent timestamp from submission time.

---

## C7. Current portal is not an electronic signature implementation

A checkbox plus localStorage does not meet the previously agreed e-consent architecture.

The current implementation lacks:
- authenticated identity binding;
- signed document copy;
- participant/researcher signature evidence;
- server-held immutable consent record;
- withdrawal workflow;
- versioned consent artifact receipt.

### Required fix

Treat current consent UI as a mock only.

Do not describe it as completed e-TCLE/e-ICF infrastructure until the approved electronic signature/e-consent flow is implemented and reviewed.

---

## C8. Regulatory overstatement: self-declared U.S. "statutory exemption"

The new governance memo states that the project "falls under statutory exemption criteria under 45 CFR §46.104(d)(2)" and AG-012 describes the exemption as effectively established.

This is too strong.

The better position remains:
- the Common Rule is not automatically applicable to privately funded research with no federal nexus;
- if a federal nexus later exists, an exemption analysis may be relevant;
- OHRP recommends investigators not independently make exemption determinations because of conflict-of-interest concerns.

### Required fix

Replace:
- `statutory exemption`
- `Exempt Equivalent`
- statements asserting that §46.104(d)(2) is definitively satisfied

with language such as:

`No U.S. federal Common Rule trigger has been identified under the current privately funded, non-FDA design. If the Common Rule becomes applicable, exemption eligibility must be determined by the appropriate institutional/regulatory authority rather than self-declared by the investigator.`

Do not use exemption as the primary legal basis when the better threshold question is applicability.

## C9. Brazilian regulatory architecture is outdated/inconsistent in the new documents

The new memo repeatedly frames:
- "CEP/CONEP platform";
- CONEP as current coordinating architecture;
- CNS 466/2012 and 510/2016 as if they were the primary governing framework.

The current legal architecture is based on:
- Lei 14.874/2024;
- Decreto 12.651/2025;
- SINEP;
- INAEP;
- CEPs.

Older CNS/Conep instruments may remain useful where still compatible, but should be described as complementary/transitional rather than as the current primary architecture.

### Required fix

Update all new governance and portal copy to use current SINEP/INAEP/CEP terminology.

---

## C10. Incorrect LGPD research legal-basis statement for a for-profit LLC

The jurisdiction matrix states:

`LGPD Art. 7, IV (Estudos por órgão de pesquisa)`

as the project research basis.

ANPD guidance explicitly states that private for-profit legal entities cannot rely on the special "órgão de pesquisa" legal basis merely because they conduct research.

### Required fix

Remove this as the generic HelpUS LLC basis.

Create a treatment-purpose matrix mapping:
- participant identity;
- consent evidence;
- scientific responses;
- security logs;
- communication records;
- retention;
- international transfer

to the actual LGPD legal basis applicable to each purpose.

Do not conflate research ethics consent with LGPD legal basis.

---

## C11. Overbroad privacy claims

The matrix claims alignment with:
- CCPA/CPRA;
- GDPR Art. 89;
- "US Cross-Border Data Framework";
- HIPAA/de-identification best practices.

These statements are too generic and in some cases inapposite.

For example, HIPAA is not a general de-identification law for this non-covered-entity cybersecurity study.

### Required fix

Use jurisdiction-specific applicability language, not global compliance assertions.

Do not claim `GDPR compliant`, `CCPA compliant`, or HIPAA alignment unless the actual territorial/material scope and implementation have been mapped.

---

## C12. "Zero commercial bias", "predatory fees", and similar language must be removed

The new governance text describes Brazilian review as eliminating commercial bias and characterizes fee-for-service IRBs as potentially "predatory".

This is inappropriate in a scientific/regulatory dossier.

A fee does not establish bias, and a free review does not establish absence of bias.

### Required fix

Use neutral language:
- "publicly administered ethics review";
- "no review fee charged to the project";
- "independent ethics review".

Remove comparative or adversarial language about commercial IRBs.

---

## C13. "Complete academic objectivity" and similar absolute claims are not defensible

The portal says that absence of commercial IRB fees "safeguards complete academic objectivity" / "guaranteeing total independence".

This is an unsupported absolute claim.

The PI is founder/equity holder and developer of the system; therefore the correct approach is transparent COI disclosure plus safeguards, not a claim of total objectivity.

### Required fix

Replace absolute claims with:
- "operational independence";
- "independent ethics review";
- "conflict-of-interest disclosure";
- "blinding and pre-specification safeguards".

# 3. HIGH-PRIORITY HARDENING

## H1. Public /experts deployment must not be mistaken for an approved live study

The route may remain deployed for technical demonstration, but until G9 approval it must visibly state on every relevant screen:

`SYNTHETIC DEMONSTRATION — NO REAL PARTICIPANT DATA COLLECTION — G9 PENDING ETHICS APPROVAL`

Do not expose a workflow that visually resembles an approved live recruitment portal without this persistent banner.

## H2. Expert IDs must not be manually selectable in production

The current UI allows selecting `EXP-01` etc.

For real collection, expert identity must be bound server-side to the invitation/session token.

Participants must not be able to impersonate another pseudonym.

## H3. Remove answer-like scenario hints

Current scenario data includes explicit prose such as:

`CR:H - confidentiality is high...`

Even if these fields are intended as context, they directly suggest the expected expert answer.

The expert should receive factual asset/context/control facts, not pre-labeled CR/IR/AR recommendations.

## H4. "Double blind" terminology should be used cautiously

The design can strongly blind experts to AI predictions and peer judgments.

But the PI created the scenarios and protocol, so "double blind" may not accurately describe all parties.

Prefer:
- `blinded independent expert review`
- `experts blinded to model predictions and peer responses`

unless a formal double-blind definition is satisfied.

## H5. Authorship charter should remain contingent

The son's role is correctly stated as contingent in one section, but no production governance document should list authorship as earned until substantive work is actually documented.

Use CRediT after contribution, not prospectively as a guarantee.

## H6. FIRST wording remains appropriately cautious

The new positionality document is mostly aligned with prior guidance.

Continue to avoid:
- "FIRST member" unless formally verifiable;
- FIRST endorsement;
- official representation.

Participation in meetings/discussions may be described factually if evidence is retained.
