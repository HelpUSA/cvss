## 2. Required Revisions for Gate G9

1. **CEP Routing**: The protocol must state "CEP competente de acordo com a classificação de risco e tramitação do SINEP", rather than demanding an "accredited CEP"; do not self-classify risk.
2. **Methodological Terminology**: Replace the term "double-blind" with **"blinded independent expert-reference evaluation"**.
3. **Explicit Risk Section**: Add an explicit protocol risk section without predeclaring "minimal risk". Technical scenarios must be explicitly certified as synthetic, authorized, or de-identified.
4. **TCLE Enhancements**:
   - Replace definitive "minimal risk" with nuanced description.
   - Use "pseudonymized/coded" rather than "anonymized" as long as a re-identification key exists.
   - Include expected study duration.
   - Explicitly declare absence of guaranteed direct individual benefit.
   - Detail participant withdrawal rights and data handling procedures upon withdrawal.
   - Include provisions for research-related harm indemnification and reimbursement policies where applicable.
   - Remove mandatory CPF requirement unless required by the local CEP.
   - Accept broad digital signatures (not exclusively ICP-Brasil/GOV.BR).
   - Add signature line and date for the Principal Investigator.
5. **Data Retention**: Include an explicit **five-year data/document retention policy** in the Data Management Plan.
6. **MARIAH Framework Role**: Keep the MARIAH framework as an orientative supporting assessment only, never a substitute for institutional CEP review.

## 3. Required Revisions for Gate G10 & Two-Stage Custody Model

1. **Two-Stage C1/C2 Custody Architecture**:
   - **Stage 1 (Reference Release)**: Authorized expert reviewers receive input scenarios under strict custodian control while developers remain completely blind.
   - **Stage 2 (Machine Unseal)**: Only after expert ratings and adjudications are finalized, locked, and cryptographically committed, the machine unseal to the frozen HelpUS execution runner takes place. Experts must never view HelpUS outputs prior to reference lock.
2. **G10 Technical Hardening**:
   - Explicit key threshold ($m$-of-$n$).
   - Documented key recovery mechanisms.
   - Role-based granular permissions.
   - Hash-chained append-only access log.
   - Isolated execution runtime.
   - Frozen hashes for source code, runtime, dependencies, model, and configuration.
   - Network egress filtering policy.
   - Ephemeral handling of decrypted data in memory.
   - Receipt of sealed raw outputs.
3. **Pre-Specified Failure Policy**:
   - Define a clear failure policy distinguishing forbidden scientific reruns from narrowly permitted infrastructure retries (e.g., power loss before any interpretable output is exposed, strictly verified against identical frozen hashes).
