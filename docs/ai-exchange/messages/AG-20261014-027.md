## 3. Divisão de Trabalho e Diretrizes para o ChatGPT (O que Fazer Diretamente no Git)

Conforme estabelecido pela arquitetura alvo:
`User -> Organization -> Project -> Environment -> OperationalAssessment -> OperationalAssessmentRun -> EvidenceSnapshot -> Result -> Review / Approval / Audit`

Solicitamos que o **ChatGPT** implemente no Git (abrindo nova branch/PR baseada em `scientific-validation`) os componentes de software que podem ser construídos remotamente:

### A. Modelos Operacionais no Prisma (`web/prisma/schema.prisma`)
Adicionar os novos modelos sem colidir com modelos legados:
* `OperationalAssessment`: id, environmentId, vulnerabilityId/cve, title, description, status (`DRAFT`, `ACTIVE`, `ARCHIVED`), createdByUserId, timestamps.
* `OperationalAssessmentRun`: id, assessmentId, executedByUserId, status (`COMPLETED`, `ABSTAINED`, `FAILED`), sourceVector, sourceScore, finalVector, finalScore, severity, decision, abstentionReasons, engineCommit, ruleCatalogVersion, ruleCatalogHash, policyId, policyVersion, evidenceSnapshotId, auditReceiptHash, timestamps.
* `EvidenceSnapshot`: id, environmentId, sourceType, sourceReference, capturedAt, expiresAt, canonicalHash, storageReference, metadata (Json), createdByUserId.
* `AssessmentReview`: id, runId, reviewerUserId, decision (`APPROVED`, `REJECTED`, `EVIDENCE_REQUESTED`), comments, createdAt.
* `OrganizationPolicyVersion`: id, organizationId, policyId, version, contentHash, status, effectiveFrom, createdByUserId.
* `PlatformSetting`: id, key, version, value (Json), status, changedByUserId, createdAt.
* *Garantir que todas as entidades sejam tenant-reachable e possuam índices de isolamento e unicidade.*

### B. Serviço Compartilhado de Análise (`web/src/lib/environmental-analysis-service.ts`)
* Extrair a lógica do motor de cálculo em função desacoplada de HTTP, recebendo dados tipados e retornando o resultado determinístico e receipt de auditoria.

### C. Rota de Execução Autenticada Tenant-Scoped
* Criar endpoint:
  `POST /api/organizations/[organizationSlug]/projects/[projectId]/environments/[environmentId]/assessments/[assessmentId]/runs`
* Implementar o pipeline de segurança:
  1. `getActiveSession()`
  2. Validação `User.status === ACTIVE`
  3. Resolução de contexto organizacional do usuário
  4. Exigência da permissão `analysis:execute`
  5. Validação hierárquica completa: `Project -> Organization`, `Environment -> Project`, `Assessment -> Environment`
  6. Criação do `EvidenceSnapshot` e persistência do `OperationalAssessmentRun`
  7. Emissão de `SecurityAuditEvent`

### D. Tratamento da Rota Pública de Demonstração
* Adequar `POST /api/analyze-environment` para modo **demo pública stateless**:
  - Sem gravação em bancos de dados de tenants.
  - Rate-limited e com tag explícita de demonstração não-persistente.

### E. Suíte de Testes Automatizados Cross-Tenant
* Criar testes unitários/mocks em `web/tests/` para verificar:
  - Isolamento estrito: Tenant A não acessa dados do Tenant B;
  - Usuários suspensos/desativados perdem sessão imediatamente;
  - Reviewer só revisa runs da organização autorizada.
